# PulseIQ — deployment

The FastAPI backend and the frontend in one container, served from a single
origin. That is deliberate: it removes the CORS preflight, and it avoids the
browser blocking an HTTPS page that tries to call `http://localhost:8001`,
which is what breaks a split frontend/backend deployment.

Target host is **Render's free tier** — no credit card, no cost.

## Before you start

You need a GitHub account and a Render account. Render deploys from a Git
repository, so the code has to live on GitHub first.

## Deploying

**1. Copy the models in.** They sit next to your local backend and are not
duplicated here, so run once from inside `pulseiq-space`:

```
python prepare.py
```

That copies about 13 MB into `ml_assets/`, and deletes anything a previous run
left behind that is no longer needed. Nothing exceeds GitHub's limits, so no
Git LFS setup is required.

**2. Push to GitHub.** Create an empty repository, then:

```
git init
git add .
git commit -m "PulseIQ"
git branch -M main
git remote add origin https://github.com/YOUR-USERNAME/YOUR-REPO
git push -u origin main
```

Use your real username and repository name. No angle brackets — on Windows `<`
and `>` are redirection characters and the command fails before git sees it.

Check `git status` first and confirm `pulseiq.db`, `secret.key` and
`vault_files/` do **not** appear. `.gitignore` excludes them; that database
holds password hashes and the key signs your login tokens.

**3. Deploy on Render.** Sign in at render.com. If **New → Blueprint** is
available, point it at the repository and `render.yaml` configures everything.
Otherwise use **New → Web Service**, pick the repo, and set: runtime **Docker**,
branch **main**, instance type **Free**, and — under Advanced — health check path
`/api/health`. Add two environment variables: `PULSEIQ_JWT_SECRET` (any long
random string) and, optionally, `GROQ_API_KEY` from console.groq.com/keys.
Without the Groq key the AI assistant reports that it is not configured on this
server; everything else works.

The first build takes 10–15 minutes, most of it installing torch.

## What to expect the first time it starts

The server answers requests within seconds, but the held-out metrics are not
ready immediately. Scoring all 327 test windows with both models takes a couple
of minutes on a shared CPU, so it runs on a background thread rather than
blocking startup — otherwise the port would not bind in time and Render would
kill the deploy as unresponsive.

While that runs, the Explainability page says *"Preparing explanations…"* and
retries, and the dashboard's reliability card says *"Measuring on held-out
data…"*. Predictions, waveforms, login, messaging, medicines, the vault and the
map all work immediately. Nothing displays a placeholder number while the real
one is still being computed.

`/api/health` reports the warm-up state if you want to watch it directly.

## Free-tier realities

**512 MB of RAM is the real constraint, and it is close.** Measured on a real
boot of this exact code: the base stack (numpy, scipy, scikit-learn, FastAPI)
sits at 158 MB, CPU-only torch adds roughly 180 MB, and SHAP — which loads only
when someone opens the Explainability page — adds another 114 MB on top. That
lands around 450 MB at peak, inside 512 MB but without much room.

The build is trimmed for exactly this: the 11.5 MB multimodal checkpoint is not
shipped (the API never loads it), pandas was replaced with numpy, SHAP is
imported only on demand rather than at startup, and torch runs single-threaded.

If the logs show the service killed with **exit status 137**, that is the kernel
out-of-memory killer. Check first that the torch install came from the CPU index
— if that step failed and pip fell back to PyPI, you get the CUDA build, which
alone uses 455 MB and cannot possibly fit. If it is genuinely just too tight,
Render's 1 GB Starter plan or Google Cloud Run's free tier at 2 GB will both
hold it comfortably.

**It sleeps.** Render suspends a free service after 15 minutes without traffic,
and waking takes about a minute — plus the warm-up again, since the container
starts fresh. Open the URL a few minutes before you present.

**Storage is ephemeral.** The filesystem resets on every deploy and every wake,
so accounts, messages, medicine logs and uploaded vault files do not persist.
Fine for a demo. If you need them to survive, that requires a paid instance
with a disk.

## Configuration

| Variable             | Default                     | Effect |
|----------------------|-----------------------------|--------|
| `GROQ_API_KEY`       | *(unset)*                   | Set → chat uses Groq. Unset → chat looks for a local Ollama. |
| `GROQ_MODEL`         | `llama-3.3-70b-versatile`   | Which Groq model answers |
| `PULSEIQ_JWT_SECRET` | generated by Render         | Signing key for session tokens |
| `PULSEIQ_STATE_DIR`  | `/data` in Docker           | Where the database, JWT key and uploads are written |
| `OLLAMA_BASE_URL`    | `http://localhost:11434`    | Local-model server, when no Groq key is set |
| `PORT`               | injected by Render          | Listening port |

Secrets are read from the environment only. They are never written to disk,
logged, or returned to the browser. Do not put either key in a file here.

## Why these versions are pinned

Three pins are load-bearing rather than cautious:

`scikit-learn==1.9.0` — your `.joblib` models were pickled by 1.9.0. Loading
them under a different version raises `InconsistentVersionWarning`, which
scikit-learn documents as possibly producing invalid results.

`numpy==2.4.6` — squeezed from both sides. `feature_engineering.py` calls
`np.trapezoid`, which does not exist before numpy 2.0, so 1.x makes every
prediction raise `AttributeError`. But shap depends on numba, and the newest
numba supports numpy only up to 2.4 — ask for 2.5 and pip backtracks all the way
to a 2023 numba source tarball that refuses to build on Python 3.12, which is
exactly how the first deploy failed. 2.4.6 satisfies both.

`numba` and `llvmlite` are pinned to the versions that resolution settles on, so
the resolver cannot wander into that hole again.

The container uses Python 3.12 because these publish wheels for 3.12 upward.

## Running the container locally first

Worth doing before you push, so a build failure appears on your machine rather
than in the deploy logs:

```
docker build -t pulseiq .
docker run -p 8001:8001 -e GROQ_API_KEY=your_key pulseiq
```

Then open `http://localhost:8001`.

## Honest note on the model

The metrics this app displays are its own measured performance on held-out ICU
data, including the AAMI SP10 and BHS grades, shown as measured rather than
dressed up. Every screen states that an estimate is not a diagnosis. The
multimodal ECG+PPG+PTT result is reported from the project's evaluation report
and flagged research-only, because its PTT feature is derived using the true
blood-pressure label — it is not, and must not be presented as, a live endpoint.
